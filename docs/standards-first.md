# Standards-first development

Use this approach when people need to keep working with their files after replacing an app, or when separate tools need to agree on the same result. A project that already has users can begin with its existing files and behavior. Write down what travels across tools, keep one useful example executable, and widen the contract as real use requires it.

## Start with a small portable workflow

1. **Name the portability test.** Describe what someone should be able to do with ordinary tools. For example, open a template in a text editor, replace named fields using a set of values, and compare the result with the app's output. For a knowledge base, open an article and its attachments without running the publishing tool.
2. **Inventory existing files and behavior.** Read representative exports, parsers, validators, and import flows. Preserve existing files when possible. Record existing behavior that is awkward to reproduce or depends on the app. Decide which behavior belongs in the contract before extending it.
3. **Use the simplest suitable format.** Start with established formats and documented conventions when they meet the portability goal. Define a project-specific profile only where the workflow needs additional rules. Prefer human-readable text and ordinary folders for material people edit. Use CSV for flat records and a structured format when relationships, sparse fields, stable IDs, or provenance need to survive exchange. Keep reusable definitions independently shareable from saved values and generated results.
4. **Specify observable results.** Define how text is decoded, names are matched, escapes work, values are validated, and output is ordered. Spell out the difference between an absent value, an empty string, and any explicit unset marker. State when defaults apply, which branches are evaluated, and whether inserted text is interpreted. Define identity independently from display labels. Separate required rules, configurable defaults, and example choices.
5. **Ship one complete example and one shared fixture set.** Start with synthetic inputs that cover a real workflow. Include the authored file, values, exact expected output or error, and a short manual walkthrough. Use a small set of additional cases for ambiguity, including Unicode, escapes, repeated references, missing or empty values, and conditional output. Specify line endings and output order where meaningful. Keep expected results under review as part of the contract.
6. **Test the portability promise.** If people should be able to open and edit a file with ordinary tools, walk through the example with those tools and verify that the app can read the edited file. If separate implementations should produce the same result, run shared fixtures through the product and a small independent implementation. State which behavior the check covers. Where copying files between installations is part of the promise, export from the actual app, import into a fresh library, and verify the user-visible result.
7. **Publish the profile and its limits.** Link the specification, example, and test commands from the app README. Give each supported profile a clear identity. Change an exchange version when the contract needs an incompatible change or a new mode of interpretation. An unchanged envelope version by itself says little about support for newer syntax. State how older readers recognize unsupported features and how users can keep or recover old data.

## Keep product behavior outside the portable result

Describe the observable output independently of how it is used. In a text tool, ordered named sections can serve a form, a clipboard action, a file export, or an email workflow. Verification, focus, retries, keyboard shortcuts, and destination navigation belong in the app or a separate delivery layer. Test that changing the delivery options leaves the rendered output the same.

Separate field declarations from rendered text once choosing a value can affect a branch without displaying the value itself. Conditions should use stable IDs or an explicitly typed Boolean. Labels help people choose and can change independently of IDs. Make emitted text explicit when it differs from the displayed label. Use literal, single-pass substitution so a value that contains template markers stays data. Add grammar only when it replaces identifiable repetition in a real example. Start with substitution and add small, composable features before considering a general-purpose language.

Treat saved input, exported output, and session state as different things. A reusable definition should travel without private responses. An editable prefilled file needs clear rules for unanswered fields and defaults. Import should never imply that an old response passed a fresh verification. For merged archives, define both the collision policy and how references follow remapped IDs. For CSV, define what blank cells and malformed short rows mean. Keep generated text and any saved responses visible to the user before export.

## What VeraFlow verified

KB Forge supplied the portability test. Its collection uses Markdown with YAML front matter and ordinary asset files. Its specification distinguishes collection requirements from configurable choices. VeraFlow adapted the same principle to user-authored templates and saved values. [KB Forge standard](https://github.com/iandorsey00/kb-forge/blob/main/docs/standard.md)

VeraFlow's first profile kept both existing version 1 JSON envelopes. A plain UTF-8 template accepted repeated, case-sensitive field references and preserved inserted text literally. The synthetic booking example used a stable choice ID, a human-readable label, a conditional note, and ordered email parts. The native app's rendering code and an independent Python reader use the same exact fixtures. The browser test exports the definition, imports it in a fresh library, fills it, and checks the actual prepared parts. Separate app tests cover CSV empty cells, sparse saved values, and relationship-preserving archive merges. [First portable profile](https://github.com/iandorsey00/veraflow/blob/v0.9.1/docs/portable-templates.md) · [Shared fixtures](https://github.com/iandorsey00/veraflow/blob/v0.9.1/examples/portable/cases.json) · [Fresh-library test](https://github.com/iandorsey00/veraflow/blob/v0.9.1/tests/ui/portable-template.spec.ts)

The first profile also exposed limits. A field declaration emitted text wherever it was placed, which made routing-only fields awkward. Legacy Email Mode coupled the output model to a single product workflow. The later `.veraflow` and `.vf` profile separated field metadata from the body, added Boolean and blank conditions, and used ordered named sections for output. It kept a plain template header-free. Navigation between sections affects delivery only. Prefilled copies distinguish an omitted key that takes the default, a null response that suppresses it, and an explicitly empty string. The app moved from the built-in Workspace interface to ordinary template folders and CSV input while retaining legacy library data. [Source file guide](https://github.com/iandorsey00/veraflow/blob/main/docs/veraflow-language-draft.md)

## Maintain the portable contract

- **Keep the conformance kit together.** A short contract, one worked example, one fixture file, and one check that runs both implementations are enough to start. Prefer one canonical spec per profile and link to it from user guides. Pin examples or give them a profile identifier so an older spec can still be tested when the UI changes.
- **Scope compatibility claims to the evidence.** VeraFlow's independent reader covers the first profile. Application tests and examples cover the advanced syntax. Identify which profiles and behaviors each check verifies, including rendering, archive validation, import collisions, and migration.
- **Separate current product instructions from archive history.** Keep the original exchange rules intact, mark implementation notes with their applicable release, and link to the current workflow. Review both links and old-file examples when retiring features.
- **Define supported features as well as version numbers.** Keep envelope, syntax profile, and app version distinct. Add an explicit profile marker or supported feature declaration when ambiguity can make an older tool silently produce different output. For a new profile, include a test showing that unsupported syntax gets a clear error rather than a plausible but wrong result.
- **Keep releases proportional.** Test the file contract wherever it runs and smoke-test the application boundaries that changed. A parser fix can usually use existing release checks plus a targeted fixture. A new exchange profile calls for independent reproduction and old-file compatibility. Clipboard automation, installers, and updates have their own platform checks. Avoid a second app or service just to prove the same format renders consistently.

Before calling a profile portable, give its published files and walkthrough to someone with ordinary tools. They should be able to reproduce the example, see what a different implementation promises to support, and understand what will happen to files they already have.
